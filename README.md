# ai-chat

用 C++ 实现的 AI 助手。核心链路：

```
浏览器请求 → 解析 → 敏感词检查 → 计算 token → 调用大模型（流式）→ 以 SSE 逐字返回
```

模型是 DeepSeek，支持推理模型的思考内容展示；token 用量取自上游统计的真实值。

## 编译与运行

```bash
cd /home/lv/ai-chat
cmake -B build
cmake --build build -j
./bin/ai_chat
```

**必须在项目根目录启动**——`.env`、`./web`、`dict/sensitive.txt` 都是相对当前工作目录解析的。

> 新增或删除 `src/` 下的 `.cpp` 后，要重新执行 `cmake -B build`。构建脚本用的是
> `file(GLOB ...)`，它不会自动发现新文件，只跑 `cmake --build` 会报符号未定义。

## 敏感词过滤

请求进大模型**之前**先扫一遍用户输入，命中就**直接返回一句固定话术、不调用模型**——
既做内容拦截，也省掉一次 API 调用（实测命中路径约 30ms，正常回答约 1.5s）。

匹配用的是 **AC 自动机**（Aho-Corasick）：启动时把词表建成「字典树 + 失配指针」，
之后每次扫描的代价是 `O(文本长度 + 命中数)`，**与词表大小无关**——所以词表从 7 条换成
几万条，单次请求的耗时也不变。

命中的词**只记在服务端日志，不回给客户端**，否则等于告诉对方该绕开哪个词。

词表支持重叠（`dict/sensitive.txt` 里刻意放了几组），例如扫描「网络赌博网站」会同时
报出 `网络赌博`、`赌博`、`赌博网站`——其中 `赌博` 是前者的后缀、后者的前缀，靠失配指针
才能报全。

### 历史与本轮的处置不同

既然 `messages` 是客户端给的，历史就是**不可信输入**，必须全量复查。但两类消息的处置
不一样，因为「本轮」和「历史」的含义不同：

| | 含义 | 命中时 |
|---|---|---|
| **本轮**（最后一条 user） | 用户现在想说的 | **拒绝整个请求**——改一句重发即可 |
| **历史**中的 user 消息 | 已经发生过的事 | **就地替换成 `[该内容已被过滤]`**，本轮照常进行 |

历史不能用「拒绝」来处理——否则一次命中会让**之后每一轮都带上那段历史**，请求次次被拒，
对话就**永久锁死**了。替换而不是删除，是为了不破坏 `user`/`assistant` 的配对结构。

前端也遵守同一条纪律：**只有「模型参与过」的轮次才进 `history`**。被拦截的一轮模型根本
没被调用，界面照常显示提示，但**不该混进发给模型的上下文里**——否则等于把服务端的话术
冒充成"模型说过的话"。

前端靠响应头 `X-Ai-Chat-Blocked: 1` 判断本轮是否被拦截（该头由 `Access-Control-Expose-Headers`
显式暴露给前端）。不用「响应里有没有 usage」之类的间接信号来判断，是因为那会把"被拦截"
和"调用出错"两种情况混为一谈。

## 前端 Markdown 渲染

助手的正文会用 `web/markdown.js` 渲染成 HTML（用户的提问和思考过程保持纯文本）。
支持代码块、行内代码、粗体、斜体、标题、列表、引用、链接、分隔线；不认识的语法
**原样显示成纯文本**——宁可不渲染，也不渲染错。

### 一条不能违反的规则：先转义，再变换

模型可以输出 `<img src=x onerror=...>`，而且用户能用提示词诱导它这么做。所以渲染器
的流程必须是：

```
1. 先把 & < > " ' 转义成 HTML 实体
2. 再在转义后的文本上做 Markdown 替换，且只产出白名单标签
```

**顺序绝不能反。** 先变换再转义会把渲染器自己生成的 `<strong>` 也转义掉，渲染直接失效；
先转义再变换，则模型给的任何 HTML 都已被中和成纯文本——**安全性是构造出来的，而不是
靠事后过滤**。这也是为什么没有直接引入 marked.js：它允许原始 HTML 直通，必须再配一层
DOMPurify，两层都得对才行。

改动渲染器后，用浏览器打开 `/markdown-test.html` 跑一遍用例（含 XSS 载荷）。该页用
`textContent` 显示结果，所以**即使转义有漏洞，页面也只会报 FAIL，不会真的执行载荷**。

### 流式过程中的不完整语法

流式返回时 Markdown 是**不完整**的（半截的 `**`、没闭合的代码块）。渲染器的处理是
**每收到一块就用最新的完整文本重新渲染整段**——不完整时退化成原样显示，标记一闭合就
自动变正确，不需要任何特殊处理。代价是 O(n²)（实际量级可忽略），以及流式期间选中文字
会被 DOM 重建打断，这是所有流式富文本的固有代价。

## Token 估算

发送前要大致知道这次请求有多大（将来做长度检查和成本预估都要用）。真正的分词器是
DeepSeek 私有的，而 tiktoken 是 OpenAI 的分词器——用它算 DeepSeek 的 token 只是
**换一个近似**，还要多跑一个 Python 服务。所以这里不用外部服务，而是**用实测数据拟合
一个估算模型**：

```
单条消息 ≈ 30.5
        + 0.526 × 汉字数
        + 0.663 × 英文词数
        + 0.250 × 词内额外字母数（长单词会被 BPE 拆开）
        + 0.331 × 数字数
        + 0.618 × 符号数

整段对话 ≈ 30 + 2 × (消息数-1) + Σ 各条内容的估算
```

### 长度检查（三层防御）

| 层 | 做什么 | 为什么放在这 |
|---|---|---|
| **HTTP 层** | 请求体超过 **1 MB** → `413` | 挡住"发个几十 MB 请求"这种粗暴滥用，**不需要任何 token 知识** |
| **应用层** | prompt 估算超过 `MAX_PROMPT_TOKENS`（默认 32000）→ 拒绝，不调模型 | 估算误差只有 1 token 级，阈值可以贴近真实上限而不误伤 |
| **上游** | DeepSeek 真正超长时返回 400 | **只有上游知道真正的上限**——我们的估算永远只是估算 |

超限被拒时返回的 SSE 消息会带 `X-Ai-Chat-Blocked` 标记，前端因此**不会把这一轮写进
历史**。否则那条超长消息会一直留在上下文里，之后每次请求都再次超限。

`MAX_PROMPT_TOKENS` 是**自我保护阈值**，不是模型的上下文上限——可以按需要调。

### 这些系数是怎么来的

用 19 个**控制变量**的样本（纯中文不同长度、英文词数、超长单词、数字、符号、代码、
中英混合）各发一次真实请求，从响应的 `usage.prompt_tokens` 取真值，再用最小二乘拟合。

| | 平均绝对误差 | 最大误差 |
|---|---|---|
| 旧的"一个汉字/一个单词算一个" | **29.7 token** | 40 |
| 本模型（训练集） | **1.01 token** | 4.0 |
| 本模型（6 个未参与拟合的留出样本） | **1.46 token** | 3.7 |

留出样本的意义：证明它不是对训练数据的过拟合。实际使用中日志会打印
`上游真实用量 输入=N（估算 M，误差 M-N）`，可以持续观察偏差。

**关键认识**：旧算法的误差几乎全部来自那条 **30 token 的固定开销**（系统提示 + 消息模板），
它完全没有被计算。内容本身的误差很小。

### 边界

- **系数只对当前模型成立**。换模型（比如 `deepseek-v4-pro`）后必须重新测一轮再更新
- 它永远只是估算。**精确值只有上游返回的 `usage` 才有**，而且它在事后
- 所以它适合做「发送前的粗筛」，不能用于计费

## 多用户与登录

服务监听 `0.0.0.0`，**同网段任何人都能访问**，而每次请求都会消耗 `.env` 里那把
DeepSeek key 的额度。所以现在有了用户体系：

- 注册需要**邀请码**（`REGISTER_CODE`）——否则任何人注册新号就能继续白嫖额度
- 登录成功后服务端发放**随机会话令牌**，客户端每次请求带 `Authorization: Bearer <token>`
- 每个用户有独立额度（`INITIAL_QUOTA`），请求结束后按上游返回的 `usage` **原子扣减**
- 登录、注册、额度都在网页右上角和登录遮罩里完成

### 数据怎么存

用户与会话存在 **SQLite**（`DB_PATH`，默认 `./data/ai_chat.db`）。选它是因为：
单文件、**有事务**、进程内并发安全、不需要额外的数据库服务。

```sql
users(id, username UNIQUE, password_hash, quota, created_at)
sessions(token PRIMARY KEY, user_id, expires_at)
```

- **密码用 PBKDF2-HMAC-SHA256 + 每用户随机盐**（12 万次迭代），存成
  `pbkdf2$迭代次数$盐$哈希`。**绝不存明文**——参考项目就有这个毛病（列名叫
  `password_hash`，插进去的却是明文）
- **令牌是不透明随机串**，服务端只存令牌本身。好处是**可以单独撤销**（删一行），
  不像 JWT 那样只能换密钥让全员掉线

### 几个关键设计

- **鉴权挂在 `pre_routing_handler` 上**，只守 `/v1/` 和 `/api/me`：
  静态文件必须放行（否则连登录页都看不到），`OPTIONS` 预检也必须放行
  （浏览器按规范不会在预检里带 `Authorization`，拦了跨域全废）
- 中间件把身份写进 `thread_local`，供 handler 读取。之所以可行：httplib 的中间件和
  handler 在**同一个工作线程顺序执行**，而且中间件对每个请求都会跑——只要它开头先清空，
  就不会读到上一个请求的残留
- **额度扣减是一条原子 SQL**：`UPDATE ... SET quota = quota - ? WHERE id = ? AND quota >= ?`，
  看受影响行数判断成功与否。**不能**"先查再扣"，并发下会双花
- **扣减发生在回答结束之后**（那时才有 `usage`），所以最后一个请求可能略微超额
- 登录失败统一回「用户名或密码错误」，**不区分用户不存在还是密码错**，避免账号枚举
- 前端按**用户名分键**存会话（`ai-chat.sessions.v1.<username>`），同一浏览器换账号
  不会看到上一个人的对话

### 它挡不住什么

| 挡不住 | 说明 |
|---|---|
| 拿到令牌的人 | 令牌就相当于登录态；丢了就是丢了 |
| 打满额度 | 有额度的人仍可以疯狂发请求——**限流还没做** |
| 明文传输 | 局域网 HTTP 下，能嗅探流量的人可以抓走令牌和密码 |

如果要把服务暴露到公网，这还不够——那需要 HTTPS。

另外要记住一条：**任何将来能触达模型的入口，都必须同样守门**。参考项目就栽在
"正门有锁、后门没门"上——它的 chat-server 有完整的 JWT 和配额，但旁边的网关一行
鉴权都没有，还监听所有网卡。

## 用量明细、限流与会话清理

### 用量明细

每次请求结束后往 `usage_log` 表记一行（用户、模型、输入/输出/思考/合计 token、时间），
统计用 SQL 的 `SUM` 直接聚合：

```
GET /api/usage   （需要登录）
→ { "today": {"requests":2,"prompt":66,"completion":202,"total":268}, "month": {...} }
```

网页顶栏的「用量」按钮会显示今日与本月。

**写入是尽力而为的**：写日志失败只打一条日志，不影响已经扣掉的额度和本次请求。
扣减与写日志是两条独立语句、**不是原子的**——但额度才是权威数据，日志丢了只是少一条统计。

### 限流（按用户）

现在有身份了，不必再按 IP 限——按 IP 会误伤共享出口 IP 的场景。

- **按用户的令牌桶**，状态只放内存（单进程下即全局；限流的目的是保护服务，不该反过来给数据库加压）
- 只作用于 `/v1/` 聊天接口，`RATE_LIMIT_PER_MINUTE` 控制长期速度，`RATE_LIMIT_BURST` 允许突发
- 超限返回 `429` + `Retry-After: <秒>`，前端会提示"请求太频繁"
- 重启后桶清空——可以接受

**注意**：`/api/login` 和 `/api/register` **还没有限流**。它们没有身份可用，只能按 IP 限，
而这个缺口意味着**密码可以被在线爆破**——这是接下来该补的。

### 过期会话清理

`sessions` 表只增不减会慢慢变大。做法是在**每次登录时顺手删掉已过期的行**：

```sql
DELETE FROM sessions WHERE expires_at < ?
```

不需要后台线程：过期行只在「有新登录」时才可能堆积，表因此自我平衡。
`expires_at` 上建了索引，删除不会全表扫描。

## 多会话与本地持久化

侧边栏可以新建、切换、删除会话；全部会话存在浏览器 localStorage 里，**服务端依旧
无状态，一行没改**。刷新页面会回到刷新前所在的会话。

### 存的是「界面上显示过的全部消息」

会话里存的是**你看到过的每一条消息**，包括被敏感词拦截的轮次、模型的思考内容、以及
token 用量。这样刷新后能完整还原——如果只存「模型参与过的轮次」，那句「触发到了知识
盲区」会在刷新后凭空消失。

而**发给模型的上下文是从它派生的**：

```
session.messages（界面显示的全部）
    │  剔除被拦截的轮次（被拦截的轮次里 user 和 assistant 两条都打了标记，
    │  否则过滤后会留下一条没有回复的孤儿 user 消息）
    │  截断到最近 20 条
    │  往前推到第一条 user（截断点可能落在问答中间）
    ▼
messages（实际发给模型）
```

两处界面上的体现：请求体面板的「累积的上下文」显示的是派生结果，而左侧消息区显示的是
全量。**两者条数不同是正常的。**

### 两个容易踩的点

- **storage key 带版本号**（`ai-chat.v1`）。将来结构变了就换成 `v2`，旧数据自然失效——
  不用写迁移代码，也不会因为读到旧结构而崩
- **提交时按 `sessionId` 而不是「当前会话」**。生成期间用户可能切走，回复必须落回发起
  它的那个会话，否则会写到错误的对话里

## 模型白名单

接口接受 OpenAI 风格的 `model` 字段，取值范围由 `ALLOWED_MODELS` 限定：

- 不传 `model` → 用 `.env` 里的 `DEEPSEEK_MODEL`
- 传了且在清单里 → 用它
- 传了但不在清单里 → **400**，并列出可用模型

回给客户端的每个 SSE 分片里，`"model"` 报告的是**实际用到的模型**，而不是硬编码的字符串。

### 为什么要有清单

- **成本**：不同模型价格可能差几倍，不能让调用方点名最贵的那个
- **错误信息**：模型名拼错时，上游的错误往往埋在 SSE 里，很难定位；白名单能在本地就给出清楚的 400
- **最容易被忽略的一条**：token 估算的系数是按具体模型拟合的（见上一节）。**白名单里的每个模型都必须单独测过系数**，否则长度检查会悄悄失准

所以清单里目前只放 `deepseek-flash`——只有它是测过的。真要用别的模型时，先测一轮再加进去。

## 接口

`POST /v1/chat/completions`，请求体是 OpenAI 的子集：

```json
{
  "model": "deepseek-flash",
  "stream": true,
  "messages": [
    { "role": "user",      "content": "我叫小明" },
    { "role": "assistant", "content": "好的小明" },
    { "role": "user",      "content": "我叫什么？" }
  ]
}
```

**接口是无状态的**，和 OpenAI 一样：多轮上下文的全部机制就是客户端每次把**完整对话**
放进 `messages` 发过来——**没有单独的 `history` 字段**，也不需要发明一个。最后一条
必须是 `role=user`，它代表本轮输入。

服务端有两个相关的保护：

- **截断**：最多携带最近 20 条消息，超出就丢掉最早的部分。截断后会往前推到第一条
  `user` 消息，避免开头的 `assistant` 成为孤儿（所以实际条数可能略少于 20）
- **敏感词分治**：见下一节

响应为标准 OpenAI 风格 SSE：

- 思考过程：`data: {"choices":[{"delta":{"reasoning_content":"…"}}]}`
- 正式回答：`data: {"choices":[{"delta":{"content":"…"}}]}`
- 用量：`data: {"choices":[],"usage":{"prompt_tokens":…,"total_tokens":…}}`
- 结束：`data: [DONE]`

## 验证

```bash
# 看流式效果（-N 关闭 curl 自身缓冲，否则会误以为没有流式）
curl -N -X POST http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"你好"}]}'

# 敏感词拦截：应立刻返回固定话术，且服务端日志打印命中明细
curl -N -X POST http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"讲讲网络赌博网站"}]}'

# 响应头应包含 Content-Type: text/event-stream 与 Transfer-Encoding: chunked
curl -s -D - -o /dev/null -N -X POST http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"hi"}]}'
```
